# AuthenticateAndGetToken

## Function and scope

`AuthenticateAndGetToken` occupies main.go:397-421. It is the whole of the program's interaction with the Vault server after a client (cert-authenticated HTTP client) exists: one cert-login call, one client-side token installation, one token-lookup call, and the extraction of one string. It takes a `VaultClient` interface (main.go:79-83, three methods: `CertLogin`, `SetToken`, `TokenLookUpSelf`), the parsed `*AppConfig` (main.go:30-40) and a `context.Context`, and returns `(string, error)` (main.go:397). The interface exists so the function can be driven by `MockVaultClient` in tests (main_test.go:30-46) while production passes `&RealVaultClient{Client: authClient.GetVaultClient()}` (main.go:85-97, :513). The ctx is the signal-cancellable context built in `run` (main.go:465-467).

Scope boundary: this function does configuration reading, PIN handling, PKCS#11, TLS and lifecycle — none of that. It assumes the `*vault.Client` it is handed already carries the client certificate through the HTTP client (main.go:349-374). It never persists anything; the only value it produces is the returned string.

## Inputs and outputs

Inputs: `client VaultClient` (non-nil, non-nil inner `*vault.Client` — established by the callers, not checked here; the constructors always return non-nil on nil error, main.go:155-174, :273-313, and `loginAndClose` builds the wrapper at main.go:513); `appConfig *AppConfig` from which only `CertAuthName` and `CertAuthMount` are read (main.go:398); `ctx` passed to both network calls (main.go:398, :412).

Outputs: `(string, error)`. On success the string is the lookup response's `data.id` (main.go:416-420), which the caller prints unchanged to stdout (`fmt.Println(token)`, main.go:498) — the documented `VAULT_TOKEN="$(yubivault -yubi)"` contract (README.md:102-105). On failure the string is `""` at every return site (main.go:400, :403, :407, :410, :414, :418). Three errors are generated locally ("auth field not found in response", main.go:403; "client_token not found or empty", :407; "token id not found or not a string", :418) and three are the library errors returned verbatim (:400, :410, :414). No error message contains server-supplied data.

Side effects: one POST to `/v1/auth/{cert_mount_path}/login` (api_auth.go:2966-2989) and one GET to `/v1/auth/token/lookup-self` (api_auth.go:5544-5566); a mutation of the shared `*vault.Client`'s token modifier (main.go:409 → request_modifiers.go:54-62).

## Invariants

1. The returned token is the *lookup* value, not the login value: `id, ok := tokenResp.Data["id"].(string)` and `return id, nil` (main.go:416-420). The unit-test fixture deliberately uses different strings for the two (`"test-token"` vs `"my-id"`, main_test.go:50-56).
2. Auth presence is checked before the token is read: `if resp.Auth == nil` at main.go:402 precedes `resp.Auth.ClientToken` at :405; empty `ClientToken` is rejected at :406-408 before `SetToken` is reached at :409. The library's own token validation would accept an empty string (`printable("")` is true, request_modifiers.go:300-306, :327-333), so this check is the only guard on the value handed to `SetToken`.
3. Ordering is load-bearing: `SetToken` (main.go:409) must precede `TokenLookUpSelf` (:412) because the token is carried in the client's request modifiers and cloned into each subsequent request as `X-Vault-Token` (request_modifiers.go:54-62; client_requests.go:177, :263).
4. Six distinct exits, each `("", err)` on failure; nothing is rolled back, so after a failure at or after :409 the shared client remains configured with the token from the login response (the library's `ClearToken`, request_modifiers.go:70, is never called anywhere in this repo).
5. The `id` extraction is type-safe from the caller's perspective: comma-ok assertion (main.go:416) means a missing key, JSON `null`, nil `Data` map, or a numeric/other JSON type produce the local error, not a panic or a malformed token string. Note the decoder keeps numbers as `json.Number` (response.go:142), so a numeric `id` would fail the string assertion.

## Assumptions

- **Non-nil responses.** The function dereferences `resp` (main.go:402, :405) and `tokenResp` (:416) whenever err is nil. The library does not guarantee non-nil here: `parseResponse` returns `(nil, nil)` for an empty body (response.go:126-128) and `sendRequestParseResponse` forwards that pair once `isResponseError` has accepted the status as 2xx (client_requests.go:188-197; errors.go:65-69). No test in main_test.go exercises a nil response with a nil error (mock returns literal fields, main_test.go:38-46).
- **Server response shapes.** `auth.client_token` on cert login, and a string at `data.id` on lookup-self, are assumed. The client side of that assumption is only field mapping (response.go:44-46, :16-26) and the OpenAPI-generated paths (api_auth.go:2966-2989, :5544-5566). Shapes the function does not read at all: `resp.WrapInfo` (response.go:35-38) and `resp.Auth.MFARequirement` (response.go:61).
- **Unvalidated config fields.** `CertAuthName` and `CertAuthMount` are not covered by `requireForMode` (main.go:142-153 requires only mode-specific fields). An empty mount reduces to `WithMountPath("")` → the library default `"cert"` (request_option.go:109-116; request_modifiers.go:233-238); an empty name is omitted from the JSON body (`json:"name,omitempty"`, schema/model_cert_login_request.go:9-12). The server decides the outcome.
- **Transport behaviour.** Each call is retried up to `RetryMax: 1` (main.go:326-342; client_requests.go:349-364; DefaultRetryPolicy, client_configuration.go:346-360), so the login POST can be transmitted twice — observed by `TestNewVaultClient_RetriesOnce`, which counts 2 attempts for a `CertLogin` against a 503 server (main_test.go:564-580). Each call also gets its own 30s deadline derived from `requestTimeout` (main.go:318-321, :329; client_requests.go:165-170).
- **Context usage.** Cancellation acts only through the two library calls; the function adds no check of its own (main.go:397-421). `run` re-checks `context.Cause` after the call (main.go:494-496), and a pre-cancelled context is exercised against a real client in main_test.go:437-471.

## Calls

- `client.CertLogin(...)` (main.go:398) — interface method (main.go:79-83); concrete `RealVaultClient.CertLogin` (main.go:89-91) → `vault.Client.Auth.CertLogin` (api_auth.go:2966-2989, path `/v1/auth/{cert_mount_path}/login`, mount escaped from `WithMountPath`) → `sendStructuredRequestParseResponse` (client_requests.go:133-158) → `sendRequestParseResponse` (client_requests.go:160-197). Error propagates verbatim (main.go:399-401). Failure modes reachable from here: non-2xx → `*ResponseError` with decoded `errors[]`/`error` or raw body (errors.go:65-113); transport error, ctx cancellation or 30s timeout → error with nil response (client_requests.go:186-197); 2xx with empty body → `(nil, nil)` (response.go:126-128).
- `client.SetToken(clientToken)` (main.go:409) — interface method → `RealVaultClient.SetToken` (main.go:92-94) → `vault.Client.SetToken` (request_modifiers.go:54-62) → `validateToken`/`printable` (request_modifiers.go:300-306, :327-333). Error propagates verbatim (main.go:409-411). The single error mode is the non-printable-character rejection, driven by server-supplied bytes; `MockVaultClient.SetTokenErr` (main_test.go:33, :41-43) is declared but never assigned, so the tests never exercise it.
- `client.TokenLookUpSelf(ctx)` (main.go:412) — interface method → `RealVaultClient.TokenLookUpSelf` (main.go:95-97) → `Auth.TokenLookUpSelf` (api_auth.go:5544-5566, GET `/v1/auth/token/lookup-self`, authenticated with the token just installed). Error propagates verbatim (main.go:412-415). Response decoding: generic `parseResponse` decodes `data` into `map[string]interface{}` with `UseNumber()` (response.go:131-159, :139-142), or, when the body has no `data` element, decodes the whole body into `Data` (response.go:152-159).
- `vault.WithMountPath(appConfig.CertAuthMount)` (main.go:398) — library request option closure; it returns no error itself (request_option.go:109-116) but the option-application error at api_auth.go:2968-2971 becomes part of the `CertLogin` error propagated at main.go:399-401.
- `fmt.Errorf` (main.go:403, :407, :418) — standard library; produces the three local errors, none of which interpolates server data or wraps another error.

## Callers and shared state

`loginAndClose` (main.go:507-514) is the only production caller and calls it at main.go:513, wrapping the same `*vault.Client` the `VaultAuthClient` holds (main.go:49-51, :63-66) in a new `RealVaultClient` (main.go:85-87). Its deferred `authClient.Close()` (main.go:508-512) runs after this function returns on both outcomes, which is how the PKCS#11/crypto11 context (main.go:63-77) is released. `run` calls `loginAndClose` at main.go:493 and prints the result at main.go:498 after re-checking `context.Cause` (:494-496). Tests call it directly with a mock (main_test.go:58, :72, :85, :99, :115) — several passing `ctx == nil`, which the mock ignores (main_test.go:38-46) — and indirectly through `loginAndClose` against a real client (main_test.go:437-471).

Shared, mutated state reachable from here: the `*vault.Client`'s `clientRequestModifiers.headers.token` (written at main.go:409, read per request at client_requests.go:177/263, never cleared); the same client object seen by the wrapper held in `run` (main.go:493, :513); the PKCS#11 context closed by the caller's defer; the process-wide stdout receiver of the returned token (main.go:498, README.md:102-105); and the HTTP client/transport with its client-certificate `GetClientCertificate` hook and environment-derived proxy settings (main.go:349-374). The function reads and writes no package-level variables.

## Open questions

- Whether a 2xx with an empty body is reachable from the real server (making `resp`/`tokenResp` nil with a nil error at main.go:402/:416). Not excluded by vault-client-go@v0.4.3 (response.go:126-128, client_requests.go:188-197); unclear; need to inspect server behaviour or vault-client-go's own `client_requests_test.go`/`response_test.go`.
- What the server returns for an MFA-gated cert login — `resp.Auth.MFARequirement` (response.go:61) is never read, so such a response, if it omits `client_token`, lands on main.go:407. unclear; need to inspect Vault/OpenBao source.
- Whether `data.id` from lookup-self is always a JSON string for the token issued here (vs redacted, absent, or numeric, which `UseNumber()` would make a `json.Number`, response.go:142). unclear; need to inspect the server's token store or a recorded real response.
- Whether a deployment can force response wrapping on cert login (`wrap_info` with no `auth`), which the function would report as "auth field not found in response". unclear; need to inspect server-side wrapping behaviour.
- Whether the `SetToken` non-printable rejection (request_modifiers.go:300-306) is reachable from a real server-supplied token; no test assigns `MockVaultClient.SetTokenErr` (main_test.go:33, :41-43). unclear; need a fixture or the server's token character-set rules.
- Whether the login `client_token` and the lookup `id` can differ in a real deployment, and which of the two a caller should export. The function returns the lookup value by construction (main.go:416-420); the fixture shows they can differ as values (main_test.go:50-56). unclear; need to inspect how the server populates `id` on lookup-self.
