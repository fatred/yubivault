# clientTLSConfig

## Function and scope

`clientTLSConfig` (main.go:349-355, doc comment main.go:345-348) builds and returns a `*tls.Config` whose only non-default settings are a `GetClientCertificate` callback that always returns `&cert` (main.go:351-352) and `MinVersion: tls.VersionTLS12` (main.go:354). Its stated purpose, in the comment, is to present the client certificate even when the server's advertised CA names do not include the client certificate's issuer, and to match what vault-client-go's own `WithTLS` would do (main.go:345-348). The certificate comes from the caller; the -local path builds it with `tls.X509KeyPair` (main.go:165) and the -yubi path from crypto11's `FindAllPairedCertificates` plus `selectCertificate` (main.go:301-303, function at main.go:214-240).

## Inputs and outputs

Input: one `tls.Certificate` by value (main.go:349). Output: a non-nil `*tls.Config` (main.go:350). There is no error return, no I/O, no logging, and no mutation of the argument — the closure captures its own copy, so writes to the caller's variable after the call would not be visible. The config is then wrapped by `newHTTPClient` (main.go:363-374), which clones `http.DefaultTransport` (main.go:364), replaces `DialContext` with a 5s dialer (main.go:365, `dialTimeout` at main.go:320) and stores this config in `transport.TLSClientConfig` (main.go:366); the resulting `*http.Client` is passed to `vault.New` via `vault.WithHTTPClient` (main.go:328-329). Because no `WithTLS` option is used, vault-client-go's TLS-override branch is skipped (`configuration.TLS.empty()` is true, $GOMODCACHE/github.com/hashicorp/vault-client-go@v0.4.3/client.go:112-121, `empty()` at client_configuration.go:363), so the config built here is what the transport keeps.

## Invariants

The callback ignores its `*tls.CertificateRequestInfo` and returns `&cert, nil` (main.go:351-352): no branch, no error, same pointer every time. Crypto/tls honours that literally: when `GetClientCertificate` is set the library returns its result without running `CertificateRequestInfo.SupportsCertificate` ($GOROOT/src/crypto/tls/handshake_client.go:1274-1287), and `SupportsCertificate` is where the advertised-CA comparison (`bytes.Equal(x509Cert.RawIssuer, ca)`) lives ($GOROOT/src/crypto/tls/common.go:1549-1576). So no CA-name, signature-scheme or version filter is applied before the certificate is sent; the only remaining selection step is the later `selectSignatureScheme` at CertificateVerify, which can fail the handshake if the server's `signature_algorithms` and the key's types do not intersect ($GOROOT/src/crypto/tls/handshake_client_tls13.go:781-787; TLS1.2 at $GOROOT/src/crypto/tls/handshake_client.go:800; `selectSignatureScheme` requires `PrivateKey.(crypto.Signer)`, $GOROOT/src/crypto/tls/auth.go:261-266).

Version policy: TLS 1.2 is a hard floor (main.go:354; filter at $GOROOT/src/crypto/tls/common.go:1245-1247) and the ceiling is unset, so the offered list is the toolchain's [TLS1.3, TLS1.2] ($GOROOT/src/crypto/tls/common.go:1219-1224 with the MinVersion==0/TLS1.2 skip at :1239-1241 and `maxSupportedVersion` at :1259-1265; toolchain pinned as go 1.27.0 in go.mod:7). On this toolchain the explicit floor is redundant for a client, since MinVersion==0 already drops everything below 1.2; it remains a pin against older toolchains.

Server authentication is untouched by this function: no `RootCAs`, `InsecureSkipVerify`, `ServerName`, `CipherSuites`, `Certificates` or `VerifyConnection` are set (main.go:350-355), so verification uses the system store and net/http fills in `ServerName` from the URL host when empty ($GOROOT/src/net/http/transport.go:1781-1789). README.md:92 records the same assumption; the test has to add `RootCAs` itself to trust its own server (main_test.go:552-553).

Finally, the returned config is live shared state: it is stored in the transport (main.go:366), shallow-cloned per connection ($GOROOT/src/net/http/transport.go:1783, clone at :3444) and written to after this function returns — ALPN `NextProtos` by the HTTP/2 setup ($GOROOT/src/net/http/http2.go:311, $GOROOT/src/net/http/internal/http2/transport.go:563-564) and `RootCAs` by the test (main_test.go:552-553).

## Assumptions

The design assumes `cert.PrivateKey` is a `crypto.Signer` that stays usable: `tls.X509KeyPair` validates key/cert correspondence and sets `Leaf` (main.go:165, $GOROOT/src/crypto/tls/tls.go X509KeyPair body), and crypto11 returns `PrivateKey` with `Public()`/`Sign` on a PKCS#11-bound type (certificates.go:159-164, keys.go:390, rsa.go:584, ecdsa.go:304). It assumes Vault advertises CA names that do not include the client certificate's issuer — the comment states this from operational experience (main.go:345-348) — and that Vault terminates TLS itself so the certificate actually arrives (PKI-SETUP.md:155). It assumes one certificate serves every request, retry and reconnect in a run (main.go:328-329 with RetryMax 1 at main.go:334-336; one transport per client at main.go:364), that redirects never carry the certificate to another host (main.go:370-372), and that the process trust store is what authenticates Vault (README.md:92). It also assumes the environment's proxy, if any, is not a TLS client-cert peer — nothing separates proxy TLS from target TLS: dialConn hands the proxy host to the same `addTLS` that clones this config ($GOROOT/src/net/http/transport.go:1928-1933), and this Go has no `ProxyTLSClientConfig` field.

## Calls

This function calls nothing: it constructs a `tls.Config` literal (main.go:350-355) and a closure (main.go:351-352). Its only outbound behaviour is through the callback: `crypto.tls.(*Conn).getClientCertificate` invokes it when a CertificateRequest arrives ($GOROOT/src/crypto/tls/handshake_client.go:1274-1277; callers at :727 for TLS 1.2 and $GOROOT/src/crypto/tls/handshake_client_tls13.go:749 for TLS 1.3), and `selectSignatureScheme` may subsequently fail the handshake (handshake_client_tls13.go:781-787, handshake_client.go:800, auth.go:261-266). Because the callback never errors, no error attributable to it can propagate; handshake failures that do occur originate in the stdlib stages above and surface through net/http, vault-client-go and then `run` (main.go:505-511).

## Callers and shared state

Sole production caller: `newVaultClient` (main.go:326-342), which invokes it inline as `newHTTPClient(clientTLSConfig(cert))` (main.go:329); that is reached from `CreateLocalVaultClient` (main.go:169) and `CreateYubikeyVaultClient` (main.go:306), i.e. from `run` via the -local/-yubi branch (main.go:480, main.go:484). Test caller: `TestClientTLSConfig_PresentsCertDespiteAdvertisedCAs` (main_test.go:551-554), which reuses the returned config in `newHTTPClient` and then writes `cfg.RootCAs` (main_test.go:552-553). Shared state is the captured `cert` (main.go:351-352, including the file-parsed or PKCS#11-backed private key) and the single `*tls.Config` object that the transport, its per-connection clones and the h2 setup all read or write (main.go:366; $GOROOT/src/net/http/transport.go:1783; $GOROOT/src/net/http/http2.go:311).

## Open questions

Which handshake path a real Vault serves (HTTP/1.1 clone vs HTTP/2 AddConn) and which CA names it advertises are unverified — no live server was contacted; the callback ignores the advertised list either way (main.go:351). Whether an https:// proxy asking for a client certificate would receive this one is not exercised, though the code path reuses the same config ($GOROOT/src/net/http/transport.go:1928-1933). The effect of a FIPS build on the offered version list ($GOROOT/src/crypto/tls/common.go:1236-1238) and the actual contents of the host trust store (README.md:92) are environment-dependent and unchecked here. Whether the post-return `NextProtos` write can overlap a handshake read of the same config object is an [INFERENCE] flagged in the assumptions section; a race-instrumented run would settle it.
